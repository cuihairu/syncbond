# 调研：iroh 作为 P2P 传输层 —— 打洞成功率与中继回退

> **本文是调研输入，不是本仓结论。** 以下内容按 2026-10-28 对 iroh 的理解整理；每一条在当作本仓属性使用之前，都必须对照所附来源重新核验。来源于 2026-10-28 通过 iroh 博客索引、docs.iroh.computer 与 docs.rs 定位。

受评估的问题（todo.md P2 工作线）：**iroh 能否作为 syncbond 的 P2P 传输层，预期打洞成功率与中继回退路径如何？**

先给答案：iroh 的模型是**直连优先**——QUIC（经由 `noq`）跑在 UDP 上并尝试打洞，失败则回退到只做密文转发的无状态中继。**iroh 官方没有公布任何实测打洞成功率。** 流传的 92–98%「直连」数字是示意性营销示例，不是实测遥测。可信这些数字之前，必须先跑一个 syncbond 自己的试点去测自己的直连/中继比例。中继路径对端到端加密的同步 SDK 是站得住的：中继无状态、保持端到端加密、可替换（公共 / 托管 / 自托管），它不削弱安全模型，只影响可用性模型。

---

## 1. iroh 是什么（与本仓相关的部分）

- **无账号、按密钥寻址**：端点按公钥拨号，不按 IP。「IP 地址会失效，改用密钥拨号」（Iroh 1.0 发布公告，`/blog/v1`）；长期在做的按 NodeID 无地址拨号工作（`/blog/iroh-dns`，`iroh 0.14.0 – Dial the world`）。
- **传输层**：基于 `noq` 的 QUIC；QUIC 多路径成为 1.0 的支柱之一（`iroh 0.96.0 – The QUIC Multipaths to 1.0`），自定义传输 / `noq` 于 0.97 落地。
- **直连优先**：「最快的路径是直连，所以必要时 iroh 会尝试打洞」（项目 README）。直连 UDP 打洞在任何中继之前尝试。
- **中继回退**：「iroh 尽可能建立直连，必要时回退到中继服务器」（docs.iroh.computer 首页）。中继是**无状态**的——负责打洞与转发，「中继服务器上不存数据」，流量端到端加密（`/blog/shared-relays`）。客户端会尝试多个中继，一个不可达时「无缝切换到另一个」（`docs/add-a-relay`）。
- **部署规模**：「已在数十万设备上投入生产」（官网页脚固定文案——这是规模主张，不是成功率指标）。

## 2. 打洞成功率——实际文档里写了什么

**没有公布实测比例。** 团队只是定性描述结果，从未给出汇总百分比：

- `the-road-to-iroh-1-0`：「在大多数常规情况下我们能几乎立刻打通洞，而在少数打不通洞的企业网络里，至少还能通过中继传数据。」打洞「是个巨大工程」，达成的比例「值得骄傲」——**没有数字**。
- `iroh-0-98-0-getting-back-to-traversing-nats`：修复回归问题——「网络变化后不会重新触发打洞」「原本能打通的连接有时会卡在中继上」。没有成功率统计；数值事实是时序参数（握手后 PTO 上限 2 秒；中继重 ping 改为立即触发，最短 500 毫秒、取上次 RTT 的 3 倍，而不是最长等 5 秒）。

**流传的那些数字，各注明它究竟是什么：**

| 数字 | 来源 | 实际是什么 | 可信度 |
|---|---|---|---|
| ~95%「直连」 | iroh.computer 首页成本模型 | **示意性**成本模型假设，明确脚注「基于 95% 直连流量的示意估算，实际直连比例与成本随网络条件、用量与地区变化」 | 仅示意——非遥测 |
| 98% 直连流量 | `/blog/shared-relays` 算例 | 成本示例（2,000 端点 × 10 GB/月 ⇒ 共 20 TB，「98% 走直连」⇒ 中继 400 GB） | 示例算术，非测量 |
| 93.10% | `/blog/shared-relays` 仪表盘截图 | 某用户截图中的一项「直连数据率」指标 | 单例轶事 |
| ~92% 直连 UDP | 搜索结果片段，2025 博客文 | **未核实**——该文 2026-10-28 未能重新定位，数字无法从一手来源确认 | 未核实——不要当事实引用 |

**本评估结论**：把打洞比例视为「示意性地处 90% 中段，官方未公布实测值；其失败模式（中继回退）完全受支持且对端到端加密安全」。设计时把直连当正常路径、把中继当有预算的、预期中的回退——而不是异常。

*机制本身*可行性有独立且充分的依据（RFC 5389 / NAT 类型文献：只要两端都不是对称型 NAT，打洞就能工作；剩下的那部分用户正是中继存在的意义）。iroh 自己的口径也一致：它点名为「打不通洞」的唯一情形是「企业网络」（对称型 NAT / 防火墙出向限制）。

## 3. 中继回退路径（本评估必须钉死的部分）

- **中继模式（iroh 1.4.1，`iroh::endpoint::RelayMode`）**——四个变体，此版本没有 `RelayOnly`：
  - `Disabled` — 完全关闭中继，只直连。
  - `Default` — n0 生产中继表；监听与拨号都可用中继；直连失败时回退。
  - `Staging` — n0 预发中继，供测试/开发。
  - `Custom(RelayMap)` — 用户自备中继基础设施（自托管，或 Iroh Services 预设）。
- **中继供给**：
  - **公共** — n0 的公共中继，免费、有限速（随 iroh 增长逐步强制；`/blog/shared-relays`）。
  - **托管** — Iroh Services Pro（$19/月，共享中继，5 MB/s，含 100 GB 出向；超出 +$0.09/GB）或 Dedicated（$199/区域 + Pro）；Pro/Dedicated 中继**需鉴权**——「Protect your relays」（2026 年 7 月，`/blog/authenticated-relays`）起托管中继默认鉴权。
  - **自托管** — 在有公网 IP 的主机上跑 `iroh-relay` 二进制；内置 ACME TLS；运行免费，但可用性/延迟/运维由你负责（`docs/add-a-relay`）。
- **成本形态**（为何直连优先对 SDK 重要）：2,000 端点 / 400 GB 中继出向的共享中继算例约 $46/月，声称比同样形态的 AWS EC2 WebSocket 服务器便宜约 38–39 倍；且「直连连接不计入中继出向」。「维持约 10 万个打洞连接、每约 5 秒 ping 一下中继路径，其实非常便宜。」
- **安全姿态**：中继对端到端加密透明（只转发密文）——正是 syncbond 需要的性质；syncbond 自己的会话加密本就位于传输层之上。需要注意的安全史：`iroh 1.0.2 – iroh-relay security fix`、`iroh 1.1.0 – security fixes`、`iroh 1.4.0 – security updates and better local networking`，以及鉴权中继那次改动。这是一个有维护、有安全评审的组件，但它确实在攻击面/可用性面上——这也是 syncbond 中继承载真实流量时，更倾向自托管或已鉴权托管中继而非开放公共中继池的理由。

## 4. 与 syncbond 的契合度

syncbond 本身已无账号、按密钥寻址、端到端加密、传输无关，且已有一个**持久化、可续传的中继存储**（`crates/syncbond-core/src/relay.rs`，commit `27c139d`）——注意那是带 oplog 游标的存储，不是 WebSocket 传输：core 内没有任何网络 I/O，传输由应用在 `Transport` trait 之后注入。iroh 不会取代配对/同步协议——它取代或增强的是协议之下的*传输*：

| 方面 | 现有中继存储 | iroh 传输 |
|---|---|---|
| 拓扑 | 中心化服务器中转一切 | 直连优先（示意 95%+），失败才走中继 |
| 中继角色 | 主路径 | 回退 |
| 寻址 | 服务器地址 | 按公钥拨号 |
| 端到端加密 | 载荷级（会话加密在传输之上） | 相同——中继只转密文 |
| 无账号 | 是 | 是 |
| 依赖重量 | 无（WS 在 core） | 重（iroh + noq + quinn 栈） |
| 浏览器/WASM | 可用（WS） | 浏览器 QUIC 需要 WebTransport——另一条集成路径（0.32/0.33 起 alpha）；与原生不是同一条代码路径 |
| 运维负担 | 自己跑中继 | 公共/托管/自托管中继三种可选 |

**建议（评估交付物，不构成仓库改动）：**

1. **保留 WebSocket 中继作为最低成本的无账号路径。** 它已可用、端到端加密、且浏览器兼容；是确定性可用的路径。
2. **把 iroh 作为可选直连 P2P 传输放在 feature gate 之后采用。** 它的价值是示意直连比例所隐含的约 20 倍中继出向节省，而不是那个（未公布的）成功率本身。gate 起来能让 core 依赖保持轻量，且不影响 WASM 目标。
3. **不要按 92–98% 这些数字做容量预算。** 先跑试点（两个真实 NAT、真实设备）测出自己的直连/中继比例，再去定托管中继规格或承诺延迟；公开数字只作示意。
4. **任何承载 syncbond 真实流量的中继，优先选已鉴权的托管中继或自托管**，而不是开放公共中继池（限速 + 上述中继安全史）。
5. **iroh 下的浏览器/WASM（WebTransport 路径）单独验证**再上；WS 中继已覆盖浏览器场景。

## 5. 证据边界与后续

- **本环境无法做实测打洞**（沙箱、单一网络出口、没有第二个 NAT）。本文档只是文献结论；建议 3 里的试点是必需的实测步骤。
- 早先搜索中的「92% 直连」片段**仍未核实**——其来源博文未能重新定位，按未确认处理。
- `RelayMode`/中继相关事实以 **iroh 1.4.1**（2026-10-28 的 docs.rs）为准；该 API 在演进（0.95 新中继、0.91 中继标准、1.x 安全版本），采用时须重新核对。
