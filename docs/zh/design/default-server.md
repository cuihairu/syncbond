# 默认中继服务器设计与实施边界

状态：**2026-11-14 规划，尚未实现**。本页记录默认服务器的目录、职责与交付边界；原子任务见仓库根目录 `todo.md` 的「默认服务器实施计划」（DSR）。本页不是可用接口或部署指南；具体路由、WebSocket 消息、鉴权、错误码与上限已冻结于[中继协议 v1 契约](relay-protocol.md)（DSR-07）。

## 1. 当前状态与目标

当前只有内存传输 `MemoryTransport`，以及保存明文 `Operation` 的 `MemoryRelayStore` / `FileRelayStore`。没有服务器可执行入口、HTTP/WebSocket 服务或客户端网络适配。已有持久化中继测试验证的是存储原型，不能代表默认服务器完成。

目标是交付可选、自托管的 Rust 中继服务：两个独立设备可以经其配对，并在异步上线、断线和重启后安全续传。SDK 仍允许应用注入其他传输；“默认服务器实现”不改变无服务器优先的 SDK 定位，也不代表提供官方公共托管服务。

## 2. 目录与依赖

以下为计划目录，目前尚不存在：

```text
apps/syncbond-server/
  Cargo.toml
  src/main.rs                 # 启动、关闭、组件装配
  src/config.rs               # 配置与校验
  src/routes.rs               # HTTP / WebSocket 接口
  src/storage.rs              # 密文存储适配
crates/syncbond-relay-protocol/ # 客户端/服务器共享的版本化传输契约
crates/syncbond-transport-ws/   # Rust 客户端网络适配与续传驱动
deploy/
  Dockerfile
  compose.yaml
```

`apps/syncbond-server` 作为独立 binary crate 加入 Cargo workspace。共享 relay-protocol crate 定义外层消息、错误和上限，不承载业务合并或密钥管理。服务器和 transport-ws 都依赖它；transport-ws 另依赖 syncbond-core。core 不依赖服务器、客户端网络栈或异步运行时。服务端使用异步 I/O；核心同步 `Transport` 通过有界桥接接入，不阻塞服务端事件循环。具体网络库及版本在实现时记录和锁定。

## 3. 职责与信任边界

| 设备端 | 服务器 |
|---|---|
| SPAKE2、短码策略、身份私钥、组密钥 | 临时配对房间及握手帧转发 |
| 加解密、操作认证、合并、墓碑 | 密文持久化、序号、去重、分页读取 |
| 本地状态与接收进度原子持久化 | 通道访问控制、限流、配额、健康检查 |
| 成员撤销及新密钥安全分发 | 撤销服务访问凭证、连接管理与日志脱敏 |

服务器只能接触路由元数据、时间、大小、密文和配对协议帧；不得接收明文 Operation、配对码、身份私钥或组密钥，不保证隐藏访问模式。现有 FileRelayStore 不得直接作为远端密文服务器后端使用。签名/MAC 不提供分发保密性：包含新组密钥的轮换消息必须通过存活设备各自的安全通道加密发送；仅用旧组密钥广播新密钥无法隔离已撤销设备。

服务访问授权与端到端组授权分开：初版由部署者持有管理凭证，创建通道并签发每设备、每通道、带读写权限的随机访问凭证；设备凭证可单独撤销，服务器不建立用户账号。组 ID、设备 ID 均不是访问凭证。凭证仅通过受保护配置及 TLS 请求传递，不放 URL、不记日志；初始分发由应用/部署者完成。服务凭证撤销不能代替组密钥轮换。

## 4. 最小网络契约

权威细节——确切路由、消息结构、错误码与全部上限——见已冻结的[中继协议 v1 契约](relay-protocol.md)。本节只记录其背后的不变量。

采用 HTTP 控制/拉取接口与 WebSocket 配对转发/更新通知。WebSocket 通知只是提示，持久日志和拉取游标才是恢复依据。掉线不能丢掉未确认的数据。

- 外层协议独立带版本、请求 ID、消息类型和稳定错误码；精确版本不匹配硬失败。实际信封 JSON 必须与 Schema 对齐，未知字段策略一致；变更已有线上格式前须写明兼容性处置。
- 通道内追加加密信封，提交成功后返回单调服务器序号。幂等键为 `(channel, messageId)`；同 ID、同信封返回原序号，同 ID、不同内容显式冲突。提交失败不得返回成功或产生可读取的未提交状态。
- `pull(after, limit, maxBytes)` 按序分页，响应带实际交付末项游标及 `hasMore`；无数据时保持输入游标，禁止跳过未交付项。超前、过期或无效游标显式报错，不静默重置。序号间隙不得导致漏读。
- 帧在网络分配/组装阶段执行大小限制，不只在 JSON 解码后检查；信封、批次、拉取响应与发送队列均有界。分页按字节和条数双重约束，装不下一条时明确拒绝，不能死循环返回空页。
- 配对房间使用至少 128 位随机路由能力值，独立于短码；短 TTL、最多两个参与端、过期清理。设备端执行短码 TTL/单次使用/失败限次；服务器执行房间加入与连接尝试限流，不知道短码。
- 公开部署经 TLS 反向代理，仅本地开发允许明文连接；定义代理信任配置、浏览器 Origin 校验、心跳、超时、取消和关闭语义。

初版不实现 P2P、跨服务器联邦、多租户计费或服务端业务合并。

## 5. 默认持久化与客户端恢复

默认服务端后端规划为 SQLite，使用事务保存通道、访问凭证摘要、密文与序号/幂等索引；给出文件权限、迁移和备份恢复约定。数据库损坏或版本不兼容应启动失败，不清空重建。初版不自动删除历史；达到磁盘/通道配额拒绝追加，避免长期离线设备被静默截断。后续引入保留策略必须另定义游标过期与快照重建协议。

设备端将收到的操作、去重状态、HLC 高水位和服务器接收游标一致持久化；落盘成功后才推进已提交接收进度。发送端保持可恢复 outbox，直到服务器持久化确认；断线/确认丢失允许重发。操作的本地序号、源设备序号和服务器序号不得混用。

复制恢复与收敛的已知缺陷是该交付的前置阻断项：普通远端操作不入持久日志、HLC 接收/恢复未接通、混合因果顺序和时钟偏移下结果依赖到达顺序。需以仓库内回归测试关闭，不能以现有测试全绿替代。`Transport` 适合配对帧；离线中继复制需专门的分页驱动，不能直接把完整 oplog 塞入单帧 `sync_over()`。

## 6. SDK 与交付顺序

先交付 Rust 的两个独立进程端到端示例，随后扩展 C ABI 的外部帧驱动配对与状态持久化接口，并逐个接入 Node/Python/Go/Java/C#/C++。绑定不重复实现 SPAKE2、密钥轮换或合并逻辑。浏览器需要异步、单线程的协议驱动接口；现有 WASM CRUD 与 conformance runner 不代表浏览器网络同步完成。

交付依赖顺序：正确性修复 → 共享协议 → 服务存储/访问控制/网络 → Rust 客户端 → 独立进程验收 → 各绑定 → 部署与 CI。服务端与客户端中不互相依赖的任务可在契约冻结后并行开发。

## 7. 发布验收

- 两个独立进程经真实 socket 配对、双向同步，随后覆盖离线写入、乱序、重复投递、服务器与客户端重启、确认丢失和分页边界。
- 接收完成后客户端重启不丢远端数据；提交失败、时钟回拨和同毫秒重启有明确验证。
- 未授权/跨通道请求拒绝；撤销设备无法重新访问通道，也无法从可监听的分发流量恢复新组密钥。
- 在服务器数据库、日志和抓取的应用层消息中搜索已知明文标记，不能发现载荷、配对码和组密钥；这只验证测试链路，不能替代密码学审计。
- 巨帧、慢客户端、队列耗尽和存储配额触发有界错误；关闭服务前处理已接收提交，重启后所有已确认记录仍可读取。
- 提供可复现的本地启动、Docker Compose、TLS 代理说明、配置示例、备份恢复和升级步骤；CI 从空数据目录启动服务并运行 Rust 网络验收。

任务逐项完成并附证据之前，不将默认服务器或真实跨设备同步标为已实现。自动 nightly 与手动稳定版发布边界保持现状。
